# 参照資料の台帳

この文書は、polyisa が参照し、または使用する外部の資料とツールを、利用条件とともに一か所で管理する台帳である。台帳を設けた理由と運用の決定は [ADR-0010](adr/0010-reference-register.md) にある。ライセンスと利用条件の情報はこの文書にだけ書き、他の文書、コード、ISADL の記述、テストは、台帳の ID で資料を参照する。

## 対象

台帳には次の種類の資料を登録する。種類は ID の接頭辞で表す。

| 接頭辞 | 種類 | 例 |
|---|---|---|
| `SPEC-` | 仕様 | ISA の仕様書、プロセッサのマニュアル、ABI の文書、規格 |
| `SRC-` | ソース | 事実を確かめるために読むソースコード |
| `TEST-` | テスト | テストスイート、テストベクタ、テストデータ集 |
| `BIN-` | バイナリ | テストの入力として実行する他者のバイナリ |
| `MEAS-` | 計測データ | 公開されている命令の実行時間などの計測値 |
| `TOOL-` | ツール | 別プロセスとして実行する外部のツール |

台帳が扱うのは、著作権のライセンスと、資料に付いた利用条件である。特許の扱いは台帳では判断しない。資料の利用条件が特許に言及している場合は、その旨を備考に書き、所有者が別に判断する。

## 用途

各項目は、polyisa がその資料をどう使ってよいかを、次の用途の記号の組み合わせで示す。

| 記号 | 用途 | 内容 |
|---|---|---|
| `R` | 参照 | 読んで理解し、設計と実装の判断に使う。本文、図、表、コードを複製しない |
| `F` | 事実の記述 | 資料が定める事実（エンコーディング、定数、構造体の配置、数値）を、polyisa 自身の表現（ISADL、Rust の表、テストの期待値）で書く |
| `T` | 取得して検証に使う | テストの実行の前にローカルへ取得し、テストの入力や期待値として使う。リポジトリには入れない |
| `X` | 実行 | 別プロセスとして実行する |
| `D` | 再配布 | 資料の全部または一部をリポジトリに含める |
| `C` | コードの流用 | ソースコードを複製、移植、翻訳する |

BSD 系の資産は `D` と `C` を許可できる。GPL 系の資産と Arm の機械可読仕様には `D` と `C` を許可しない（[ADR-0013](adr/0013-license-mit-or-apache.md)）。

## 規則

1. polyisa の成果物（コード、ISADL の記述、テスト、文書）に資料の内容を反映する前に、その資料を台帳に登録する。
2. 用途は、利用条件の原文を読み、原文が許していると確認できたものだけを許可する。原文から判断できない用途は許可しない。
3. 利用条件の確認は版ごとに行う。参照する版を変えたら、確認をやり直す。
4. 台帳に登録した項目は全て確認済みとする。確認の日付や確認者の記録は残さない。
5. 成果物（`crates/`、`guests/`、`tools/` のコード、ISADL の記述、テスト、取得定義）の中で資料を参照するときは、機械可読の注記で書く。Rust のコードとテストでは `// Ref: SPEC-RISCV-UNPRIV §2.4`（`///`・`//!` の文書コメントでも同じ形）のように ID と節を書き、ライセンスの情報を書き写さない。ISADL では `reference SPEC-RISCV-UNPRIV;` と `ref SPEC-RISCV-UNPRIV "§2.4"` で書く。この書式以外の ID の言及は、検査の参照とみなさない。
6. 台帳に登録する前の資料は、成果物のいかなる用途にも使わない。ただし、利用条件を確かめるために資料を読むことは除く。設計文書での引用は記述の形を示す例示に限り、実装の根拠にしない。例示の引用は検査の対象外とする。
7. 用途の欄は `R`、`F`、`T`、`X`、`D`、`C` の組み合わせをカンマ区切りで書く（例：`R,F`）。`—` はいかなる用途の許可も表さない。`D` と `C` は BSD 系の資産に限り、原文を確認して許可する。GPL 系の資産と Arm の機械可読仕様には `D` と `C` を許可しない。
8. 開発の立ち上げに必要な道具（`TOOL-RUST`、`TOOL-GIT`、`TOOL-CURL`、`TOOL-TASK`、`TOOL-NEXTEST`）は、他の項目に先立って登録する。それまでの開発作業は、利用条件を確かめる範囲（規則 6 の例外）に位置づける。
9. ISA・ABI の事実（エンコーディング、意味論、定数、構造体の配置、動作の規則）の根拠は一次資料に限る。ISA の事実は `SPEC-` の ISA 仕様書とプロセッサの公式文書、ABI の事実は ABI の仕様書とカーネルの UAPI（`SRC-LINUX` 等、対象 OS そのものの一次資料）から取る。他のエミュレータ、アセンブラ、逆アセンブラ、コンパイラ、リンカ（QEMU、binutils、gcc、LLVM、Capstone、Unicorn、Bochs 等、二次実装のすべて）を事実の根拠（用途 `R`、`F`）に使ってはならない。「照合に使っただけ」も根拠の混入とみなす。二次実装に許される用途は `X`（オラクルとしての実行）と `T`・`BIN`（テストの入力）だけである。仕様書が黙っている事項（未割当エンコーディングの動作、実装定義の値）は二次実装の動作を写さず、設計判断として `docs/gaps.md` に記録する。

## 機械的な検査

`task refs:check` は次のことを検査し、違反があれば失敗する。この検査は `task check` に含まれ、Git のコミット前のフックでも実行される（[開発作業とローカル検証](design/dev-workflow.md)）。

1. 成果物（`crates/`、`guests/`、`tools/`）の固定書式の注記に現れる台帳の ID が、すべて台帳にある。
2. 参照された項目が台帳にあり、参照の場所に応じた用途を許可している。用途の欄に必要な記号が含まれていること。

   | 参照の場所 | 必要な用途 |
   |---|---|
   | ISADL の `reference` と `ref`、Rust のコードとテストの出典の注記（`//`、`///`、`//!` の `Ref:`） | `F` |
   | テストデータの取得定義と、`testkit` の表に書いたテストデータ | `T` |
   | `testkit` の表に書いたツールと、devtool が実行するツール | `X` |

3. テストデータの取得先（`.testdata/`）が `.gitignore` の対象であり、`git ls-files` に現れない。取得定義（`tools/testdata/manifest.txt`）がある場合は、各行の ID が台帳にあり、用途 `T` が許可されていること。
4. `guests/*/spec`、`guests/*/src`、`crates/*/src` の Rust に、二次実装の名前（`qemu`、`binutils`、`llvm`、`capstone`、`unicorn`、`bochs` の大文字小文字を区別しない文字列）が含まれていない（規則9 の走査）。`crates/testkit` はツール要求の表なので対象外。オラクル・テスト入力としての言及は `tests/` に置くため対象外。
5. 台帳と自前のライセンス文を除くリポジトリのファイルに、polyisa のもの以外の著作権表示と SPDX のライセンス識別子が含まれていない。走査するのは `Copyright`、`©`、`SPDX-License-Identifier` の文字列であり、台帳の `docs/references.md` と自前の `LICENSE-MIT`、`LICENSE-APACHE` は対象外とする。自前の `MIT OR Apache-2.0` の識別子行と `polyisa contributors` の著作権行は許可する。
6. `Cargo.lock` にワークスペース外のパッケージがない（[ADR-0001](adr/0001-no-external-crates.md)）。

設計文書と台帳は、1 と 2 の検査の対象外とする。設計文書に現れる ID は、記述の形を示す例示とみなす。設計文書での資料の参照（`R`）は、規則 1 と 6 によって管理する。

この検査は、許可されていない用途の多くを見つけられるが、すべてではない。資料の文章を言い換えて書き写した場合や、ID を書かずに資料の内容を使った場合は見つからない。規則 1 と 5 が守られていなければ、検査は違反を見つけられない。

台帳の表は `task refs:check` が読む。表の列の順序と書式を変えるときは、検査の実装も同じ変更で直す。

## 台帳

各列の意味は次のとおりである。

- ID：項目を一意に指す識別子。種類の接頭辞と名称で構成する。
- 名称：資料の書名またはツール名と、同一性の判断に必要な版情報。
- 発行者：資料を発行した組織または個人。
- 版：利用条件を確認した版。
- 対象：その資料を使う ISA ファミリ、クレート、作業。
- 利用条件：ライセンスや利用規約の名称と、原文の所在。
- 用途：許可した用途の記号。
- 備考：取得元・適用範囲・利用条件の不確かさ等の補足。
