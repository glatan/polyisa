# ISA 記述言語（ISADL）

この文書は、ゲスト ISA の静的な性質を記述する言語 ISADL と、その記述から生成するコードを定める。ISADL を採用した理由は [ADR-0002](../adr/0002-isa-description-language.md) にある。この文書の構文は設計段階の案であり、`isadl` クレートの実装時に文法の参照文書として確定させる。確定させる際に変えてよいのは綴りと細部の構文で、記述できる対象と生成物の種類は変えない。

## ISADL に書くものと Rust に書くもの

ISADL には、命令の振る舞いのうち、表として書ける部分を書く。具体的には次のものである。

- 命令のエンコーディング（ビットパターン、オペコード表、命令長の規則）
- オペランドの取り出し方（フィールド、符号拡張、連結、スケーリング）と、読み書きの別
- レジスタクラスと、それが CPU 状態のどのフィールドにあたるか
- アセンブリ構文と別名（拡張ニーモニック）
- 命令の属性（分岐、ブロック終端、メモリアクセス、例外の可能性など）
- 機能、プロファイル、CPU モデル、挙動パラメータ（[CPU モデル](cpu-models.md)）
- タイミング表（[タイミングモデル](timing.md)）

命令意味論、ヘルパー、CPU 状態の構造体、ISADL で表せない不規則なデコード処理は Rust で書く。ISADL はそれらの Rust の項目を名前で参照し、生成コードが参照の整合性をコンパイル時に検査する。意味論を ISADL に含めないのは、意味論を書ける言語を作ると、その言語の設計と処理系の実装が ISA の実装とは別の大きな作業になるからである（代替案の比較は ADR-0002）。

## ファイルの配置

ゲスト ISA クレートは、ISADL の記述を `spec/` の下に置く。

```text
guests/riscv/spec/
├── isa.isadl          ISA の宣言、デコーダの入口、レジスタクラス、実行モード
├── features.isadl     機能とプロファイル
├── models.isadl       挙動パラメータと CPU モデル
├── rv_i.isadl         基本整数命令
├── rv_m.isadl ...     拡張ごとの命令
└── timing/
    └── sifive_u74.isadl
```

ファイルの分割はコンパイル単位ではなく、保守の単位である。ファイルをまたいだ参照は名前で解決し、宣言の順序は問わない。

現状の記述面は `.isadl` テキストではなく、`guests/<isa>/spec/*.rs` が `polyisa_isadl::Model` を組み立てる Rust の DSL である（ADR-0017）。`build.rs` が spec を読み込み、`isagen` がデコーダと命令一覧を生成する。この文書の文法は、外部の道具が必要になったときのフロントエンドの設計として残す。

## 言語の要素

### ISA の宣言とデコーダの入口

`isa` は ISA ファミリの名前と、命令ストリームの読み方を宣言する。`decoder` はデコードの入口であり、一つの ISA に複数持てる。ARM の A32、T16、T32、IA-64 の命令スロットの種類ごとのデコーダ、Hexagon のデュプレックス命令のように、同じ ISA の中で異なる規則でデコードする命令群ごとに入口を分ける。

```text
isa riscv {
    parcel 16;                          // 命令フェッチの単位（ビット）
    fetch_endian little;
}

decoder rv {
    length {                            // 先頭パーセルから命令長を決める
        insn[1:0] != 0b11 => 16;
        _                 => 32;
    }
}
```

命令ストリームのエンディアンが実行中に変わる ISA（MIPS、Power、SuperH の双エンディアン）では、`fetch_endian` に実行モードを指定する。

### 実行モード

実行モードは、デコードや意味論を変える CPU 状態の一部を宣言する。デコーダは実行モードを入力に取り、ブロックキーにも実行モードが入る（[実行エンジン](execution-engine.md)）。

```text
mode thumb   : bool;        // ARM の CPSR.T
mode opsize  : enum { o16, o32, o64 };   // x86 の既定オペランドサイズ
```

実行モードの値を CPU 状態から計算する関数は Rust で書く。実行モードは数ビットから数十ビットに収め、ブロックキーの一部として 32 ビットに詰められる大きさに制限する。

### レジスタクラス

レジスタクラスは、オペランドフィールドの値をレジスタに対応させ、そのレジスタが CPU 状態のどこにあるかを示す。

```text
regclass gpr : u64 [32] {
    state   x;                              // CpuState のフィールド名
    names   x0..x31;
    abi     zero ra sp gp tp t0 t1 t2 s0 s1 a0 a1 a2 a3 a4 a5
            a6 a7 s2 s3 s4 s5 s6 s7 s8 s9 s10 s11 t3 t4 t5 t6;
    hardwired x0 = 0;                       // 読むと 0、書き込みは捨てる
}
```

生成器は、`state` で示したフィールドのオフセットを `core::mem::offset_of!` で求めるコードを出力する。窓付きレジスタ（SPARC）、回転レジスタ（IA-64）、スタック相対のレジスタ（x87）のように、フィールド値から物理的な位置を実行時に計算するレジスタクラスは `dynamic` と宣言し、位置の計算を Rust の関数で与える（[命令意味論](semantics.md) の動的なレジスタ参照）。

### フィールドとオペランド

フィールドは命令語からのビットの取り出し方を宣言する。ビット範囲の連結（`++`）、定数の連結、符号拡張（`sext`）、スケーリング（`scale`）を組み合わせられる。

```text
field rd    = insn[11:7];
field rs1   = insn[19:15];
field imm_i = sext(insn[31:20]);
field imm_b = sext(insn[31] ++ insn[7] ++ insn[30:25] ++ insn[11:8] ++ 0b0);
```

オペランドは、フィールドに型と読み書きの別を与えたものである。型はレジスタクラス、即値、PC 相対の分岐先、メモリ参照などがある。読み書きの別は、タイミングモデルの依存関係の追跡、IR の最適化、トレースでのレジスタ変化の表示に使う。命令語に現れない暗黙のオペランド（条件フラグ、HI/LO、x86 の RAX など）も、読み書きの別とともに宣言する。

ISADL のフィールドで表せない取り出し方は、Rust のフックとして宣言する。x86 の ModRM/SIB と変位、68k の実効アドレスと拡張語、VAX のオペランド指定子は、可変長の追加バイトを読みながら解釈する手続きであり、宣言的な規則で書くより Rust で書くほうが短く正確になる。フックは、命令ストリームの読み出し器を受け取り、オペランドの値と消費したバイト数を返す決まった形の関数である。LEB128 の整数と、指定したエンディアンの N バイト即値は、組み込みのフィールド種別として用意する。

```text
extern operand_kind ea(size: Size) -> MemOrReg;   // Rust: decode::ea
```

フックを使う命令でも、エンコーダを生成できるように、フックごとに逆変換（エンコード側の Rust 関数）を対で宣言する。

### 形式と命令

形式（`format`）は、複数の命令で共通するフィールド配置とオペランドの宣言をまとめる。命令（`insn`）は、形式、一致させるビットパターン、述語、構文、属性、タイミング分類を宣言する。

```text
format R {
    operands { rd: gpr = rd, write; rs1: gpr = rs1, read; rs2: gpr = rs2, read; }
}

insn add : R {
    match  0000000 ..... ..... 000 ..... 0110011;
    syntax "add {rd}, {rs1}, {rs2}";
    timing alu;
}

insn addw : R {
    match  0000000 ..... ..... 000 ..... 0111011;
    when   rv64;
    syntax "addw {rd}, {rs1}, {rs2}";
    timing alu;
}
```

命令の意味論は、既定ではゲスト ISA クレートの `sem` モジュールにある、命令と同じ名前の関数である。引数は宣言したオペランドを宣言順に受け取る。複数の命令が一つの関数を共有する場合や、CPU モデルによって意味論の関数を切り替える場合は、`sem` 句で明示する（切り替えの規則は [CPU モデル](cpu-models.md)）。

### 述語と制約

命令の宣言は、二種類の条件を持てる。`when` は機能と実行モードについての述語であり、CPU モデルと実行時の実行モードで評価する。`where` はデコードしたフィールドの値についての制約である。

同じビットパターンが CPU モデルによって別の命令になる例は多い。MIPS Release 6 は、旧来の `ADDI` のオペコードを、`rs` と `rt` の大小関係によって `BOVC`、`BEQZALC`、`BEQC` に割り当て直した。

```text
insn addi    : I  { match 001000 ..... ..... ................; when !mips_r6; ... }
insn bovc    : I  { match 001000 ..... ..... ................; when mips_r6; where rs >= rt; ... }
insn beqzalc : I  { match 001000 ..... ..... ................; when mips_r6; where rs == 0 && rt != 0; ... }
insn beqc    : I  { match 001000 ..... ..... ................; when mips_r6; where rs != 0 && rs < rt; ... }
```

x86 の `0F 05` は、80286 では `LOADALL`、AMD64 以降では `SYSCALL` である。このような重なりは `when` で区別し、どの CPU モデルでも高々一つの命令が一致することを、生成器が静的に検査する（後述）。

`where` は、フィールドと定数、またはフィールドとフィールドの比較（等価・非等価・大小）の組み合わせである。RISC-V の C.JR 群（`rs1`、`rs2` のゼロ判定）や、上の MIPS R6 のコンパクト分岐のように、固定ビットだけでは区別できない命令を記述できる。生成した線形デコーダは、パターンの一致後にフィールドを取り出して条件を評価する。静的検査は、パターンが重なる命令の組について、`where` が互いに排他か、`when` が機能の排他宣言で両立しない場合に限り重なりを許す。排他の判定は句の対ごとに行い、同じフィールド（の組）への矛盾する制約があれば排他とみなす。

### オペコード表

x86 と WebAssembly は、ビットパターンよりオペコードのバイト値による表で書くほうが仕様書の構成に近い。ISADL は、バイト値をキーとする表（`map`）と、接頭辞の宣言を持つ。表の要素は命令を直接宣言するか、別の表へ分岐する。

```text
prefix 0x66 opsize_override;
prefix 0xF0 lock;
prefix rex = 0x40..0x4F  when mode64;

map primary {
    0x00 /r : add  Eb, Gb   { lockable; timing alu_rm; }
    0x01 /r : add  Ev, Gv   { lockable; timing alu_rm; }
    0x0F    => map_0f;
    0x63 /r : arpl Ew, Gw   { when i286 && !mode64; }
    0x63 /r : movsxd Gv, Ed { when mode64; }
}

map map_0f {
    0x05 : loadall286 { when i286 && !i386; }
    0x05 : syscall    { when syscall_insn; }
}
```

`Eb` や `Gv` のようなオペランド種別は、x86 の ISADL 記述の中で、ModRM のフックと幅の規則を組み合わせて定義する。

### 構文と別名

`syntax` は逆アセンブルとアセンブルの両方に使うテンプレートである。オペランドの書式（レジスタ名を番号で書くか ABI 名で書くか、即値を 10 進で書くか 16 進で書くか）はオペランドの型から決まり、利用者が表示の設定で切り替える。x86 の Intel 構文と AT&T 構文、68k の Motorola 構文と MIT 構文のように構文が複数ある ISA では、`syntax.<名前>` で並べて宣言する。

別名（`alias`）は、特定のオペランドの値を持つ命令に別の表記を与える。RISC-V の `addi rd, rs1, 0` を `mv rd, rs1` と表示する場合や、Power の拡張ニーモニックがこれにあたる。逆アセンブラは設定に応じて別名を優先し、アセンブラは別名も受け付ける。

### 属性

命令の属性は、実行エンジンとタイミングモデルと IR が意味論を解析せずに使える情報を与える。属性の一覧は次のとおりである。

| 属性 | 意味 | 使う側 |
|---|---|---|
| `branch`、`call`、`return`、`indirect` | 制御の移動の種類 | ブロックの終端判定、分岐予測モデル |
| `delay_slot`、`likely` | 遅延スロットを持つ、遅延スロットが条件付きで無効化される | ステップの構成 |
| `ends_block` | 実行モードや CPU 状態の大部分を変えるので、ブロックをここで終える | ブロックの構成 |
| `load`、`store`、`atomic` | メモリアクセスの種類 | タイミングモデル、IR |
| `may_trap` | 例外を起こしうる | IR（例外の出口の生成） |
| `syscall`、`serializing` | システムコール、パイプラインの直列化 | 退出の生成、タイミングモデル |

### 出典

ISADL のファイルは、記述の根拠にした資料を、[参照資料の台帳](../references.md) の ID で `reference` として宣言する。命令、オペコード表の項目、タイミング表、CPU モデルには、根拠にした節を `ref` で添えられる。

```text
reference SPEC-RISCV-UNPRIV;

insn add : R {
    match 0000000 ..... ..... 000 ..... 0110011;
    syntax "add {rd}, {rs1}, {rs2}";
    timing alu;
    ref SPEC-RISCV-UNPRIV "§2.4";
}
```

`isagen` は `reference` と `ref` を生成コードに使わず、ID の書式だけを検査する。ID が台帳にあり、台帳でその資料に事実の記述（`F`）が許可されていることは、`task refs:check` が検査する。ビルドが文書に依存しないように、この検査をビルドから分けている。

## 生成物

`isagen` は、検査済みのモデルから次の Rust のコードを生成する。

| 生成物 | 内容 |
|---|---|
| 命令の型 | 命令ごとの列挙子と、デコードしたオペランドを持つ型 |
| デコーダ | デコーダの入口ごとに、ビット位置で分岐する決定木、またはバイト値の表。葉で `when` と `where` を評価する |
| 意味論の呼び出し | 命令の型から意味論の関数を呼ぶ分岐。インタプリタ向けには、命令ごとに単相化した関数ポインタの表も生成する |
| 逆アセンブラ | 構文テンプレートと別名から生成する |
| エンコーダ | フィールドの逆変換から生成する。テストでの命令列の組み立てと、JIT のホスト用機械語の生成に使う |
| メタデータ | 命令の属性、オペランドの読み書き、タイミング分類、命令の一覧 |
| レジスタ記述 | レジスタの名前、幅、CPU 状態上のオフセット、GDB の番号 |
| CPU モデルの表 | 機能集合、挙動パラメータ、識別情報、タイミング表 |

エンコーダの生成を必須にする理由は二つある。一つは、外部のアセンブラがない ISA（ローカル環境では 68k、Alpha、PA-RISC、SuperH、IA-64、VAX、PDP-11）でも、テストの命令列を Rust のテストコードの中で組み立てられることである。もう一つは、x86 と AArch64 の ISADL 記述からホスト用のエンコーダが得られ、JIT のバックエンドが命令のエンコードを別に実装しなくてよくなることである。

## 静的検査

`isagen` は、コードを生成する前に次の検査を行い、違反があればビルドを失敗させる。

1. デコードの一意性：定義済みのすべての CPU モデルと、実行モードのすべての値の組について、どのビット列にも高々一つの命令が一致する。同時に一致しうる命令の組は、明示的な優先順位を宣言した場合に限り許す。利用者が実行時に機能を足し引きして作る機能集合については、機能間の排他（`conflicts`）の宣言と組み合わせて検査する。
2. 到達可能性：どの CPU モデルでも一致しない命令は警告する。
3. フィールドの整合：形式のフィールドとパターンの固定ビットが重ならない。オペランドのビット幅がレジスタクラスや即値の型に収まる。
4. 逆変換の存在：すべてのフィールドとオペランド種別にエンコード方向の変換がある。
5. 参照の解決：機能、実行モード、レジスタクラス、タイミング分類、意味論の関数の名前がすべて定義されている。意味論の関数が存在し、引数の型が一致することは、生成コードのコンパイルで検査される。

デコードの一意性の検査は、決定木を構築する過程で、葉に残った命令の集合に対して述語の充足可能性を判定して行う。述語は機能と実行モードについての命題論理式であり、機能の数が数百でも、葉ごとの候補は数個に絞られているので、候補の組ごとに CPU モデルを列挙して判定すれば足りる。

生成器は、エンコーダとデコーダの往復の性質（エンコードした命令語をデコードすると元の命令とオペランドに戻る）を、命令ごとの乱択テストとして生成する。このテストはゲスト ISA クレートの通常のテストとして実行される。
