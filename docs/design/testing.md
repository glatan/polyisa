# 検証戦略

この文書は、polyisa の正しさを確かめる方法を定める。エミュレータの誤りは、誤った値が後の多数の命令を経てから症状として現れることが多く、症状から原因の命令までたどる作業に時間がかかる。そこで、命令単位で誤りを捕まえる検証を厚くし、プログラム単位の検証は、命令単位の検証で捕まえられない誤り（システムコール、シグナル、命令の組み合わせ）を対象にする。

## テストの前提

テストは次の前提で設計する。

- テスト用の部品は `testkit` クレートに自前で書く（[ADR-0001](../adr/0001-no-external-crates.md)）。擬似乱数、性質テストの実行器、テストベクタの読み込み、外部ツールの呼び出し、テストデータの検証に使う SHA-256 がこれにあたる。
- 外部のツールとデータはオラクルとしてだけ使い、[参照資料の台帳](../references.md) で許可された用途に限る。ツールは別プロセスとして実行する。ツールやデータがないときは、該当するテストを「未実行」として報告する（[開発作業とローカル検証](dev-workflow.md)）。
- 外部のテストデータ（公式のテストスイート、生成したテストベクタ、他の OS のバイナリ）はリポジトリに含めない。ライセンスが未定の間に、利用条件の異なるデータを混ぜないためである（[ADR-0009](../adr/0009-no-code-reuse-until-license.md)）。`task testdata:fetch` が、版とチェックサムを固定した取得元から `.testdata/` に取得する。

開発環境で使えるオラクルは次のとおりである（プロジェクト開始時点の確認による）。どのツールも、台帳に登録して使う。

| ツール | 対応する ISA | 用途 |
|---|---|---|
| clang 23 と rust-lld | x86、ARM、AArch64、MIPS、Power、RISC-V、SystemZ、SPARC、Hexagon、LoongArch、WebAssembly | テスト用プログラムのビルド、ABI の定数と構造体の配置の抽出 |
| llvm-objdump | 同上 | デコーダと逆アセンブラの差分テスト |
| gdb（全ターゲット対応） | gdb が対応する ISA | GDB の接続のテスト |
| wasmtime | WebAssembly | WebAssembly と WASI の差分テスト |
| ホストの CPU | x86-64 | ユーザーモードの x86-64 命令の差分テスト |

68k、Alpha、PA-RISC、SuperH、IA-64、VAX、PDP-11、OpenRISC には、手元に使えるアセンブラと逆アセンブラがない。これらの ISA では、ISADL から生成したエンコーダでテストの命令列を組み立て、仕様書から書いた期待値と比較する。GNU binutils のクロス版や QEMU を用意できた環境では、それらをオラクルとして追加する。

## テストの層

### 1. 基礎と基盤の単体テスト

`bits`、`softfloat`、`decimal`、`isadl`、`mem`、`engine` は、それぞれの単体テストを持つ。`softfloat` は Berkeley TestFloat が生成するテストベクタとも比較する（[浮動小数点と十進演算](floating-point.md)）。

### 2. ISADL から生成するテスト

ISADL の生成器は、命令ごとに次のテストを生成する（[ISA 記述言語](isa-description.md)）。

- エンコードとデコードの往復：乱択したオペランドでエンコードした命令語をデコードし、元の命令とオペランドに戻ることを確かめる。
- デコードの一意性：生成時の静的検査として行う。

### 3. 命令単位のテスト

裸実行環境（[実行エンジン](execution-engine.md)）で、命令を 1 つか少数だけ実行し、CPU 状態とメモリを検査する。命令列は生成したエンコーダで組み立てる。期待値は仕様書の記述から書き、根拠にした仕様書を台帳の ID と節でテストの注記に残す（[参照資料の台帳](../references.md)）。

CPU モデルによって振る舞いが変わる命令は、振る舞いの異なる CPU モデルごとにテストする。CPU モデルのグループ（[CPU モデル](cpu-models.md)）を使い、世代ごとの代表の CPU モデルを選んでテストを走らせる。

公開されている命令単位のテストデータ集（68000 や 8088 などについて、命令ごとの初期状態、終了状態、サイクル数を収録した SingleStepTests など）がある CPU では、それを取得して比較する。これらのデータ集はサイクル数も含むので、`exact` のタイミングの検証にも使える。

### 4. デコーダの差分テスト

LLVM が対応する ISA では、命令語を生成して polyisa と llvm-objdump の両方で逆アセンブルし、結果を比較する。命令語の生成は ISA の命令空間の大きさで変える。16 ビットの命令空間（Thumb、RISC-V の圧縮命令、SuperH）は全数を、32 ビットの命令空間は乱択と境界値を、x86 は接頭辞とオペコードと ModRM の組み合わせを構造的に生成する。

比較では、両者の構文の差（ニーモニックの別名、即値の書式）を正規化してから、命令として有効かどうかと、ニーモニックとオペランドの一致を見る。食い違いは、polyisa の誤り、LLVM の誤り、意図した差に分類し、意図した差と LLVM の誤りは一覧に記録して以後の比較から除く。

### 5. 適合テストスイート

| 対象 | テストスイート |
|---|---|
| RISC-V | riscv-tests、riscv-arch-test |
| WebAssembly | WebAssembly の仕様のテストスイート（`.wast`） |
| ソフトウェア浮動小数点 | Berkeley TestFloat |

WebAssembly の仕様のテストスイートはテキスト形式で書かれているので、テキスト形式の構文解析とバイナリ形式へのエンコードを、WebAssembly のゲスト ISA クレートのテスト用の部品として実装する。

### 6. ABI 表のテスト

Linux の ABI 表（システムコール番号、構造体の配置、定数の値）は、Linux のカーネルの UAPI ヘッダから抽出した値と比較する。抽出は次の手順で行う。

1. Linux のカーネルのソースから、アーキテクチャごとの UAPI ヘッダを生成する。
2. 定数の値と、`sizeof` と `offsetof` の値を配列に並べる C のソースを、clang でアーキテクチャごとのオブジェクトファイルにコンパイルする。
3. polyisa の `loader` でオブジェクトファイルを読み、配列の値を取り出して ABI 表と比較する。

この方法は、ゲストの C ライブラリを必要としないので、LLVM が対応するすべての ISA で使える。

### 7. プログラム単位のテスト

ユーザーモードで実際のプログラムを動かすテストは、三つの種類のプログラムを使う。

1. 自前のテストプログラム：システムコールを直接呼ぶ小さな実行時ライブラリと C かアセンブリのテストを、clang と rust-lld で静的にリンクする。ゲストの C ライブラリが不要なので、LLVM が対応する ISA ならどれでもビルドできる。
2. Rust のテストプログラム：rustup で追加したターゲット（開始時点で `aarch64-unknown-linux-musl` など）でビルドする。
3. 配布物のバイナリ：Linux のディストリビューションの、ISA ごとのバイナリとライブラリを取得し、ゲストのルートとして使う。busybox やコアユーティリティを動かし、出力を比較する。

期待する出力は、実機、ホスト（x86-64 の場合）、または他のエミュレータで同じプログラムを実行して得る。

### 8. 実行の差分テスト

命令列を polyisa とオラクルで実行し、ステップごとに CPU 状態を比較する。オラクルは、x86-64 ではホストの CPU、それ以外では QEMU のユーザーモード（gdb の接続で 1 ステップずつ状態を読む）を使う。命令列は、ISADL のメタデータを使って、CPU モデルで有効な命令から乱択で生成する。

食い違いが見つかったら、命令列を短くしていき、食い違いを再現する最小の命令列を報告する。

### 9. JIT のテスト

JIT の実行結果は、インタプリタの実行結果とブロックの境界ごとに比較する（[JIT](jit.md)）。層 8 と同じ乱択の命令列と、層 7 のプログラムを使う。

### 10. タイミングのテスト

忠実度が `exact` の CPU モデルは、タイミング表の出典から作った命令列とサイクル数の組で検証し、`approx` の CPU モデルは較正用のベンチマーク集で誤差を測る（[タイミングモデル](timing.md)）。

### 11. 決定性のテスト

同じプログラムを同じ設定で 2 回実行し、命令トレース、仮想時間、出力が一致することを確かめる。複数のゲストスレッドを使うプログラムを必ず含める。

## 重いテストバイナリ

次のどちらかにあたるテストを、重いテストとする。

- 外部のツールかテストデータを必要とする。
- 実行に、nextest の `default` プロファイルの時間の上限を超える時間がかかる。

重いテストは、各クレートの `tests/` の下の、名前が `heavy_<層の名前>_` で始まるテストバイナリに置く。たとえば、riscv-tests を実行するテストは `guests/riscv/tests/heavy_conformance_riscv_tests.rs` に置く。重いテストでないものは、単体テストか、名前が `heavy_` で始まらないテストバイナリに置く。層 1 と層 3 のうち外部のデータと比較するもの（TestFloat、SingleStepTests）は、`conformance` の層に置く。

| 層の名前 | 層 |
|---|---|
| `oracle` | 4. デコーダの差分テスト |
| `conformance` | 5. 適合テストスイート |
| `abi` | 6. ABI 表のテスト |
| `program` | 7. プログラム単位のテスト |
| `diff` | 8. 実行の差分テスト |
| `jit` | 9. JIT のテスト |
| `timing` | 10. タイミングのテスト |
| `determinism` | 11. 決定性のテスト |

この名前の付け方により、nextest の設定では重いテストを名前だけで選び分けられる。テストを実行する方法（タスク、nextest のプロファイル、オラクルがない場合の扱い、検証の機会）は [開発作業とローカル検証](dev-workflow.md) で定める。

## テストの網羅の記録

CPU モデルごとに、どの命令がどの層でテストされたかを記録する。記録は、ISADL の命令の一覧とテストの実行結果から生成し、手で書かない。手で書いた一覧は、命令の追加やテストの追加のたびに更新が漏れ、実際の網羅と食い違うからである。
