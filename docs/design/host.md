# ホスト抽象化

この文書は、ホストの OS とホストの CPU に依存する機能を扱う `host` クレートの設計と、ホストへの移植の方針を定める。外部クレートを使わない方針は [ADR-0001](../adr/0001-no-external-crates.md) にある。

## 方針

ホストの機能は、標準ライブラリにあるものは標準ライブラリで使い、ないものだけを `host` クレートの自前の FFI 宣言で補う。`host` 以外のクレートは、ホストの OS とホストの CPU を判定する条件付きコンパイル（`cfg(target_os)`、`cfg(target_arch)`、`cfg(target_endian)`、`cfg(target_pointer_width)`）を使わない。`std::os::unix` のように OS ごとにしかない標準ライブラリのモジュールの直接利用も `host` に限り、他のクレートは OS 非依存の `std` の範囲だけを使う。OS 差が必要な処理は `host` の API 経由で呼ぶ。例外は JIT のホストのバックエンドで、これはホストの ISA ごとのモジュールに閉じる。この規則は `task check` の検査で確認する（[開発作業とローカル検証](dev-workflow.md)）。

標準ライブラリを優先するのは、標準ライブラリが Linux、macOS、Windows、WASI の差を吸収しており、標準ライブラリで書いた部分は移植の作業から外れるからである。

## 必要なホストの機能

polyisa がホストに求める機能と、その提供元は次のとおりである。

| 機能 | 使う側 | 提供元 |
|---|---|---|
| ページフレーム用のメモリの確保 | `mem` | 標準ライブラリのメモリ確保 |
| ファイルとディレクトリの操作、メタデータ | `kernel` | `std::fs`。Unix 拡張が必要な部分は `host` 経由 |
| ソケット | `kernel` | `std::net`。Unix 拡張が必要な部分は `host` 経由 |
| スレッド（ホストの入出力の作業用） | `kernel` | `std::thread` |
| 時刻 | `kernel` | `std::time` |
| 端末かどうかの判定 | `kernel` | `std::io::IsTerminal` |
| 端末の生モードと端末の大きさ | `kernel` | `host`（Unix では `tcgetattr`、`tcsetattr`、`ioctl` の FFI 宣言） |
| ファイルシステムの情報（`statfs`） | `kernel` | `host`（FFI 宣言） |
| 実行可能メモリ | `jit` | `host`（Unix では `mmap`、`mprotect`、Windows では `VirtualAlloc`、`VirtualProtect`） |
| 命令キャッシュの同期 | `jit` | `host`（AArch64 のホストで必要） |
| ホストの CPU の機能の検出 | `jit` | `std::arch` の機能検出のマクロ |
| 割り込みキーの捕捉（実行の安全な停止） | `cli` | `host`（Unix では `sigaction`） |

ホストの入出力の待ちを `poll` や `epoll` で多重化せず、作業用のホストスレッドで標準ライブラリの阻止型の呼び出しを行う（[ユーザーモード](user-mode.md)）のは、多重化の仕組みが OS ごとに異なり、標準ライブラリに含まれないからである。

## FFI 宣言の書き方

`host` クレートの FFI 宣言は、次の規則で書く。

- 宣言は OS の系統ごとのモジュール（`sys/unix`、`sys/linux`、`sys/macos`、`sys/windows`）に置く。構造体の配置と定数の値が CPU によって異なる場合は、さらにホストの ISA ごとに分ける。
- 宣言ごとに、根拠にした資料を台帳の ID と項目でコメントに書く（[参照資料の台帳](../references.md)）。ホストの OS の文書も、使う前に台帳に登録する。
- 宣言した関数は、`host` クレートの中で安全な関数に包み、`unsafe` を外に出さない。
- 構造体の配置と定数の値は、ホスト上で実行するテストで確かめる。たとえば、端末の属性を読んで書き戻し、値が変わらないことを確かめる。

Linux のホストでは、標準ライブラリがすでに C ライブラリをリンクしているので、C ライブラリの関数を `extern "C"` で宣言すれば呼べる。システムコールを直接発行するインラインアセンブリは、ホストの ISA ごとに書く必要があるので使わない。

## ホストのエンディアンとポインタ幅

`host` 以外のクレートは、ホストのエンディアンとポインタ幅を仮定しない。

- ゲストのメモリの多バイトの値は、常に `from_le_bytes` や `from_be_bytes` などで変換する（[ゲストメモリ](memory.md)）。ホストの整数の表現をゲストのメモリに直接書き込まない。
- ゲストのアドレスとサイズは `u64` で扱い、`usize` に変換するのは、ホストのメモリの添字にするときだけにする。変換は失敗を検査する。
- CPU 状態の構造体は、ホストのエンディアンの整数で値を持つ。CPU 状態をバイト列として外部に出すとき（GDB のレジスタの転送、状態の保存）は、決まったエンディアンに変換する。

この規則の確認のため、`task check:targets` で、ISA に依存しない中核のクレートとゲスト ISA のクレートを、ビッグエンディアンのターゲット（`powerpc64-unknown-linux-gnu`）と 32 ビットのターゲット（`i686-unknown-linux-gnu`、`wasm32-unknown-unknown`）で `cargo check` する。これらのターゲットの標準ライブラリは rustup で追加し、`task doctor` がその有無を表示する。これらのターゲットでテストを実行する手段は、移植を始める段階で用意する。

## 対応するホストの段階

| 段階 | ホスト | 範囲 |
|---|---|---|
| 1 | Linux x86_64 | すべての機能。JIT を含む |
| 2 | Linux AArch64、macOS（Apple Silicon） | インタプリタから始め、AArch64 のホストのバックエンドを追加する。macOS の JIT は `MAP_JIT` と書き込み保護の切り替えが必要になる |
| 3 | Windows x86_64 | インタプリタから始める。ゲストの uid、gid、パーミッションは仮想カーネルで合成する |
| 4 | wasm32 | インタプリタだけ。ホストのスレッドがない環境では、ホストの入出力を作業用のスレッドに渡さず、直接行う |

段階 2 以降は、段階 1 の実装が安定した後に着手する。段階 1 の間は、`cfg` の使用の規則の検査と `task check:targets` によって、移植を妨げるコードの混入を防ぐ。
