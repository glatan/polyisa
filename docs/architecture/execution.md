# 命令意味論・実行エンジン・JIT

命令の実行基盤は、総称的な命令意味論（`sem`）、実行ループとインタプリタ（`engine`）、ブロック SSA 中間表現（`ir`）、x86-64 ホスト向け JIT（`jit`）の 4 クレートで構成される。

## 命令意味論と `Backend` トレイト

### 単一記述の原則とオーバーヘッドの受容

命令意味論は `guests/<isa>/src/sem.rs` に置き、`polyisa_sem::Backend` を型引数に取る総称関数として一度だけ書く。インタプリタは `InterpBackend`（具体値で即時実行）で、JIT は `IrBackend`（IR 命令として記録）で同じ関数を呼び出す。両者が同一の意味論を共有するため、インタプリタが JIT のオラクルになる。

総称バックエンド経由の整数加算は、直接 `wrapping_add` を回す実装と比べて `W64::to_u128`/`from_u128` 変換とトレイト呼び出しの固定費により約 40〜50% の上乗せが生じる（`crates/engine/tests/bench_generic_direct.rs` の release 20 万回計測で直接版約 36〜43 µs に対し総称版約 55〜61 µs）。単一命令に占める比率は小さく、浮動小数点命令では `softfloat` 側が支配的であり、高速化は JIT 層で担う方針のため、この上乗せを受け入れてトレイト形状を維持している。

なお、一部のゲスト（OpenRISC・Hexagon 等）は現行では具体値インタプリタ上に意味論を書いており、総称 `Backend` 化は未対応のままである（詳細は各 ISA 文書を参照）。

### 記述規則と全域演算

意味論の関数には二種類の値が現れる。

- **デコード時に決まる値**（レジスタ番号、即値、命令アドレス、挙動パラメータ）：通常の Rust の値として扱い、`if` / `match` で分岐できる。
- **実行時に決まる値**（レジスタやメモリの内容）：幅型（`W8`・`W16`・`W32`・`W64`・`W128`・`F16`・`F32`・`F64`）を伴う `B::V<W>` および真偽値 `B::B` として扱う。実行時の分岐は `select`・`if_then`・`if_then_else` で書く。

`Backend` の算術・シフト・除算はすべての入力で結果を定義する全域演算である。シフト量のマスクやゼロ除算時の挙動は ISA ごとに異なるため、ホスト命令の未定義動作やトラップを引き継がず、意味論側で明示的に書く。

### CPU 状態参照・例外・ステップ構成

- **CPU 状態参照**：CPU 状態構造体は `#[repr(C)]` で定義し、`StateRef<W>`（オフセットと幅）または動的配列参照 `StateArray<W>`（SPARC のレジスタウィンドウ、IA-64 の回転レジスタ、x87 スタック等）でアクセスする。
- **例外の一貫性**：例外を起こしうるロード・ストア・権限検査はレジスタ更新前に済ませ、複数ストアを行う命令では事前に `probe` で全範囲のアクセス可否を確かめる。例外時は命令開始前の状態（または `REP`・`MOVC3`・`MVCL` のように仕様が定める途中状態）を保つ。
- **ステップ構成**：多くの ISA は 1 命令を 1 ステップとするが、遅延スロット付き分岐（MIPS・SPARC・SuperH・PA-RISC・OpenRISC）、パケット（Hexagon）、バンドル（IA-64）、反復命令の 1 単位（x86 `REP`・VAX 文字列・s390 `MVCL`）もそれぞれ 1 ステップとして扱う。IR の基本ブロックを非循環に保つため、意味論の中に実行時回数のループは書かない。
- **条件フラグ**：x86・s390・m68k では遅延評価、ARM・Power では個別フィールドなど ISA に適した配置を CPU 状態に持つ。バックエンドからは通常の `get`/`set` として見えるため、IR のデッドストア削除で不要なフラグ計算を除去できる。

`Backend::call<Helper>` と `Backend::timing_hint` はトレイトに定義されているが、現行の実装では未接続（`call` は `Unimplemented`、`timing_hint` は空実装）である（[GAP-0027](../known-issues.md)）。

## 実行エンジン（`engine`）

### ループ駆動と ISA 別 `step` の分担

クレート依存規則（`engine` は `guests/*` に依存できず、`guests/*` も `engine` に依存できない）の下で実行ループを共通化するため、ループは二層に分かれている。

1. **`engine::run`**：繰り返し、ステップ予算の管理、観測点（`Observer`）とブレークポイント（`Breakpoints`）の呼び出し、`Outcome`（`Exit`・`Unimplemented`・`StepLimit`・`Deadlock`・`Breakpoint`）への集約を担う。`StepRunner` がこれを `VcpuRunner` に適合させる。
2. **ISA ごとの `step` 実装（`crates/cli/src/run_<isa>.rs` 等）**：命令フェッチ、デコード、意味論呼び出し、トラップ処理を行う。

トラップの境界は `engine::run::TrapHandler`（`handle_trap` → `TrapOutcome`）が定める。ただし RISC-V のみ `cli` 独自の `EcallHandler` 変換層が残っており、統一は未完了である（[GAP-0024](../known-issues.md)）。

### 観測点・ブレークポイント・裸実行環境（`BareEnv`）

- **`Observer`**：`pre_step`・`post_step`・`exit` のフックを提供する。観測を行わない `NoObserver` では呼び出しがインライン展開で消える。メモリアクセス単位の観測点（ウォッチポイント用）は未実装である（[GAP-0100](../known-issues.md)）。
- **`Breakpoints`**：ゲストメモリを書き換えず、`run_observed` がステップ実行前に PC を照合して停止する。
- **`BareEnv`**：OS パーソナリティなしで CPU 状態と `AddressSpace` だけを動かす最小実行環境であり、命令単位のテストや Linux が動かない旧世代 CPU の検証に使う。

### ブロックキャッシュとソフトウェア TLB の現状

`engine::cache` にブロック・ジャンプキャッシュの型、`mem` にソフトウェア TLB の型が定義されているが、現行の実行ループには接続されていない。ループは 1 命令ごとにページ表の走査と線形デコードを繰り返しており、自己書き換えコードの検出とブロック無効化も未実装である（[GAP-0028](../known-issues.md)）。

## IR と JIT（`ir` / `jit`）

### 構成と有効化

`ir` クレートは `Backend` を実装した `IrBackend` でブロック単位の SSA IR を記録し、定数畳み込み・コピー伝播・共通部分式削除・CPU 状態へのデッドストア削除といったブロック内最適化と、テスト用の IR 解釈実行器を提供する。

`jit` クレートはブロックごとの実行回数を数え、閾値を超えたブロックを IR 変換・最適化して機械語へコンパイルする。現行のホストバックエンドは **x86-64（System V ABI、Unix 系）のみ** であり、命令エンコードは `isagen` 経由で生成する。実行可能メモリは `host::exec_mem` から確保し、書き込み可能状態で生成してから実行可能へ切り替える（W^X）。それ以外のホスト（wasm32-wasi を含む）ではコンパイルが `None` を返すスタブになり、自動的にインタプリタ／IR 解釈へフォールバックする。

`polyisa run` では既定でインタプリタを使い、環境変数 `POLYISA_JIT` を設定すると JIT が有効になる。

### 現行の対応範囲と制限

- **JIT 統合済みランナ**：`aarch64`・`arm`・`x86` の 3 ISA（`crates/cli/tests/heavy_jit_diff.rs` でインタプリタとのブロック境界一致を検証）。
- **フォールバック条件**：ヘルパー呼び出しや未対応操作を含むブロックは JIT 化せず、インタプリタへフォールバックする。
- **タイミング・観測との併用**：ステップ単位の観測や GDB デバッグ時はインタプリタ経路を使う。
