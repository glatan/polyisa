# ADR-0010：参照資料と外部のツールを台帳で一元管理し、台帳で許可した用途にだけ使う

- 状態：承認
- 日付：2026-10-26
- 変更：2026-11-19 — 「確認」欄による確認の記録をやめ、台帳にある項目は全て確認済みとする運用に変更

## 背景

polyisa は 19 の ISA ファミリを対象にし、ISA ごとに複数の仕様書とマニュアルを参照する。これに加えて、ABI の文書、Linux カーネルのソース、テストスイート、テストデータ、計測データ、外部のツールを使う。これらの利用条件はさまざまである。自由なライセンスで公開された仕様書もあれば、複製や用途を制限する利用規約が付いたマニュアルもあり、GPL のソースコードもある。プロジェクトの所有者は、ライセンスの違反を何としても防ぐことを求めている。

利用条件の情報がコミットの説明、コードの注記、テストの定義に散らばると、ある資料をどの用途に使ってよいかを一度に確かめられない。版の変更に伴う確認の漏れも見つけにくい。polyisa は CI を使わないので、変更の取り込みの前に必ず通る検査は、開発者の手元の検査だけである。

## 決定

- 外部の資料とツールを、利用条件とともに [参照資料の台帳](../references.md) に登録する。ライセンスと利用条件の情報は台帳にだけ書く。
- 台帳の各項目は、許可する用途を、参照、事実の記述、取得して検証に使う、実行、再配布、コードの流用の組み合わせで示す。
- 用途は、プロジェクトの所有者が利用条件の原文を版ごとに読んで許可する。原文から判断できない用途は許可しない。
- 成果物は台帳の ID で資料を参照する。`task refs:check` が ID と用途の整合を検査し、Git のコミット前のフックでこの検査を実行する。
- ISA ファミリの実装は、その ISA の参照資料が台帳に登録されてから始める。

## 帰結

- ある資料の利用条件と polyisa での使い方を、台帳の一つの行で確かめられる。
- 成果物の中の参照と台帳の食い違いを、コミットの前に機械的に見つけられる。ただし、ID を書かずに資料の内容を使った場合は見つからないので、規則を守ることが前提になる。
- 登録した項目は全て確認済みとするため、登録後の確認の工程はない。登録の際に利用条件の原文を点検することは変わらない。
- 台帳の表の書式が検査の実装と結びつくので、書式の変更は検査の変更を伴う。

## 検討した代替案

- 出典と利用条件をコミットの説明に書く：記録が履歴に散らばり、ある資料の用途を一覧できない。
- ディレクトリごとに出典の文書を置く：同じ資料が複数のディレクトリから参照されるので、利用条件の記述が重複し、版の更新の際に食い違う。
- 人によるレビューだけで確認する：確認の漏れを止める段階が、レビューをする人の注意のほかにない。
