# ADR-0003：命令意味論をバックエンドトレイトに対して総称的に一度だけ書く

- 状態：承認
- 日付：2026-10-26

## 背景

実行方式は、インタプリタで正しさを先に固め、JIT を後から追加する方針である。その際、JIT のために ISA ごとの命令意味論を書き直さないことが要件になっている（要件 R5）。対象の ISA の数を考えると、命令の意味を二通りに書く方式では、作業量が倍になるうえ、二つの実装の食い違いが誤りの温床になる。

## 決定

命令意味論は、バックエンドトレイト `Backend` を型引数に取る Rust の関数として一度だけ書く（[命令意味論](../design/semantics.md)）。インタプリタのバックエンドは操作をその場で実行し、IR のバックエンドは操作を IR として記録する。意味論の中の Rust の制御構文は、デコード時に決まる値に対してだけ使い、実行時の値による分岐はバックエンドの操作で書く。

## 帰結

- インタプリタと JIT が同じ意味論から作られるので、両者の食い違いは IR の変換と機械語の生成の誤りに限られる。インタプリタを JIT のオラクルにできる。
- 意味論の書き方に規則が加わる。実行時の値による分岐を Rust の `if` で書くとコンパイルできないので、規則の違反の多くはコンパイル時に見つかる。
- 単相化により、インタプリタの性能は意味論を直接書いた場合に近づくと見込んでいる。この見込みは段階 1 のベンチマークで確かめる（[ロードマップ](../design/roadmap.md)）。
- 意味論の関数がバックエンドの数だけ単相化されるので、コンパイル時間と生成されるコードの量が増える。
- 同じ仕組みに、別のバックエンド（記号実行、依存関係の解析）を後から足せる。

## 検討した代替案

- インタプリタと JIT の変換器を別々に書く（QEMU の TCG 以前の方式に近い）：インタプリタを最も素直に書けるが、命令の意味を二度書くことになる。
- すべての命令を IR に変換し、IR を解釈実行する：意味論は一度で済むが、インタプリタの段階でも IR の構築と解釈の費用がかかり、JIT のない段階の性能が下がる。IR の解釈実行器は、テストのためにだけ用意する（[JIT](../design/jit.md)）。
- 意味論を ISADL のような専用言語で書く：[ADR-0002](0002-isa-description-language.md) の代替案として検討し、採らなかった。
