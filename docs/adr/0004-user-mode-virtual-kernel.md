# ADR-0004：ユーザーモードの OS のサービスをプロセス内の仮想カーネルで実装する

- 状態：承認
- 日付：2026-10-26

## 背景

エミュレーションの形態はユーザーモードであり、ゲストのプログラムに OS のサービスを提供する必要がある。QEMU のユーザーモードは、ゲストのシステムコールを構造体と定数の変換だけ行ってホストの Linux へ渡し、ゲストのプロセスとスレッドをホストのプロセスとスレッドに対応させる。

polyisa には、この方式と合わない要件がある。

- ホストは当面 Linux x86_64 だが、他の OS への移植を想定し、Linux x86_64 への依存を最小にする（要件 R7）。ホストへ渡す方式は、ホストが Linux であることを前提にする。
- 外部クレートを使わない（要件 R1）。ホストへ渡す方式では、ホストのシステムコールのほぼすべてについて、構造体と定数の FFI 宣言が必要になる。
- 既定の実行を決定的にする（設計の原則）。ホストのスレッドとプロセスにゲストの実行を任せると、スケジューリングの順序がホストで決まる。
- Linux 以外の OS パーソナリティ（WASI、Unix V7、BSD）も対象にする。

## 決定

OS のサービスは、polyisa のプロセス内で動く仮想カーネルで実装する（[ユーザーモード](../design/user-mode.md)）。ゲストプロセスとゲストスレッドは仮想カーネルの対象であり、ホストのプロセスとスレッドに対応しない。仮想カーネルは、ホストのファイル、ソケット、時刻、端末を、標準ライブラリを通して使う。

## 帰結

- 仮想カーネルは、標準ライブラリが動くどのホストでも動く。ホストへの移植で書き直す部分は `host` クレートに限られる。
- `fork` はアドレス空間の複製で、パイプと futex は仮想カーネル内の対象で実現するので、ホストの `fork` や `futex` を使わない。
- スケジューリングを仮想カーネルが行うので、ゲストスレッドの実行の順序を決定的にできる（[ADR-0007](0007-deterministic-single-host-thread.md)）。
- システムコールの意味を自前で実装する量が、ホストへ渡す方式より多い。特に、仮想ファイルシステム、シグナルの配送、`epoll` などの待ち合わせを実装する必要がある。
- ホストのファイルを共有の写像で扱う場合など、ホストの他のプロセスとの一貫性は保証できない場合がある（[ゲストメモリ](../design/memory.md)）。
- ゲストのプログラムがホストのプログラムを直接実行することはできない。

## 検討した代替案

- ホストの Linux へシステムコールを渡す（QEMU のユーザーモードの方式）：実装量は少ないが、ホストが Linux に限られ、決定性を失い、FFI 宣言が大量に必要になる。
- 両方式を併用し、Linux のホストではホストへ渡す方式を選べるようにする：二つの方式で振る舞いの差が生じ、テストの対象が倍になる。仮想カーネルの方式が安定した後に、性能上の必要が確認された場合に限り、特定のシステムコール（大きなファイルの読み書きなど）の最適化として検討する。
