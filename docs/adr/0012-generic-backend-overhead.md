# ADR-0012：総称バックエンド経由の加算の上乗せを受け入れる

- 状態：承認
- 日付：2026-11-09

## 背景

[ロードマップ](../design/roadmap.md)の段階1完了条件3は、意味論をバックエンドに対して総称的に書いた版と、インタプリタ専用に直接書いた版を代表的な命令で比較し、差を記録することを求める。差が10%を超えた場合は、原因を調べ、バックエンドトレイトの設計を見直すか、差を受け入れる理由をADRに書く。

計測は `crates/engine/tests/bench_generic_direct.rs`（200,000回、release、決定的検証ではなく記録用）で行う。直接版は `u64::wrapping_add` の素朴な繰り返し、総称版は `InterpBackend::add::<W64>` 経由の加算である。

## 決定

計測結果の上乗せ（約+40〜50%）を受け入れる。バックエンドトレイトの設計は見直さない。

- 計測値（release、200,000回あたり、5回実行のうち外れ値1件を除く中央付近）：
  - 直接 `direct`：約36〜43µs（代表値：36.4µs、36.3µs、38.1µs）
  - 総称 `generic`：約55〜61µs（代表値：55.5µs、55.4µs、55.4µs）
  - 浮動小数点加算 `fadd`（genericのみ、softfloat委譲の目安）：約72〜73µs
  - 差の目安：`(55.4 − 36.4) / 36.4 ≒ +52%`。実行ごとのぶれを除いても+40%を下回らない。
- 原因：総称版は1回の加算ごとに `W64::to_u128`/`from_u128` の変換とトレイト経由の呼び出しを挟む。直接版の1命令（`wrapping_add`）に対する固定費であり、命令意味論の1ステップに占める割合は小さい。`fadd` の費用はsoftfloat委譲が支配的で、バックエンド経由の上乗せではない。
- 受け入れる理由：総称化の利益（[ADR-0003](0003-semantics-generic-over-backend.md)：意味論を一度だけ書き、インタプリタとIRで共有する）は段階1の設計の要であり、インタプリタの定数倍の上乗せは段階1の正しさの検証を妨げない。速度が必要な用途はJIT（[ADR-0005](0005-functional-first-timing.md)のタイミング分離の方針）の段階で扱い、インタプリタの微細な高速化は行わない。

## 帰結

- `InterpBackend` と `Backend` トレイトの形状は変えない。
- 将来インタプリタの速度が問題になった場合は、このADRの計測を起点に再計測し、変換の単相化や単相化済みステップの形状の見直しを検討する。
- 浮動小数点演算の費用はsoftfloatの実装に帰属し、バックエンド経由の上乗せとは分けて扱う。

## 検討した代替案

- トレイトの `add` を `u64` 直結にして変換をなくす：`Width` の汎化が崩れ、意味論の記述が幅ごとに分かれる。ADR-0003の利益を失うため採らない。
- ベンチマークの代表命令を増やして再判定する：加算以外の命令でも固定費の構造は同じであり、結論は変わらない。必要になったらJIT段階で代表命令を広げて再計測する。
