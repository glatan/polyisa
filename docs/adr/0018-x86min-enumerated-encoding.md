# ADR-0018：x86-min のエンコーディングは変形ごとの列挙で書き、ModRM/SIB フックは将来に置く

- 状態：承認
- 日付：2026-11-15

## 背景

設計の [ISA 記述言語](../design/isa-description.md) は、x86 のような可変長 ISA に、オペコード表（`map`）、接頭辞の宣言、ModRM/SIB と変位を解釈する Rust フック（`extern operand_kind`）を用意する構想を持つ。

実装の `guests/x86/spec/x86min.rs` はこれらを使わず、オペランドの置き方（レジスタ直接、mod、SIB の有無、変位の長さ）ごとに命令を列挙する。生成された `Insn` と、命令長の判定（`fetch_len`）、ModRM/SIB バイトとオペランドの取り出し（`dispatch`）をつなぐのは `cli` の `step_x86` で、バイトの取り出しは手で書かれている（GAP-0015）。この形で x86-64 と i386 の両方について、静的リンクした BusyBox の基本コマンド群とアプレット横断テストが通っている。

## 決定

x86-min のエンコーディング記述は、変形ごとの列挙を現行の方針とする。オペコード表と ModRM/SIB フックの機構は、二番目の可変長 ISA（68k、VAX など）を実装するとき、あるいは列挙の複製が命令追加の主な費用になったときに作る。

手で書かれた境界を次のように定める。`step_x86`（`cli`）が接頭辞の解釈と命令長の判定を担い、生成された `decode` が命令語から `Insn` を定め、`dispatch` がオペランドの取り出しと意味論への振り分けを担う。`Insn` の変種は、この三層のうち生成された層までは一意性の検査が効く。

## 帰結

- ISADL と isagen に、デコード途中で可変長のバイトを読むフックと、その逆変換を対で要求する機構を今は作らない。消費者が x86-min だけの段階でこの機構を設計すると、実際の要請がないまま抽象が決まる。
- 列挙は冗長だが、各変種は独立したビットパターンなので、生成器による一意性の検査と、未対応の変種の報告（`Outcome::Unimplemented` の word 表示）がそのまま効く。
- BusyBox で観測された命令形を列挙に足す作業は、フックなしでも件数ベースで進められた（i386 のブリングアップの実績）。列挙が費用の主因になった段階で方針を再検討する。
- `x86min.rs` から `map` とフックへの書き換えは、機構が入ってから行う。

## 検討した代替案

- 今すぐ `map`・`prefix`・フックを ISADL に実装する：可変長デコードの中核機構であり、設計文書の構想とも一致する。しかし、命令語の長さを ModRM/SIB の値に依存させる段階的デコード、オペランド種別（`Eb`/`Gv`）と幅の規則、フックの逆変換とエンコーダ生成までを正しく設計するには大きな作業になる。消費者が一つしかない今、先に列挙で命令網羅を済ませたほうが、機構の設計に実際の要請を反映できる。
- `fetch_len` と `dispatch` を `guests/x86` に移す：`guests/*` は `engine` に依存できず、`dispatch` は `Backend` 総称で書けるがトラップ境界（`TrapHandler`）は `engine` の型なので置けない。現在の三層分離が依存規則の下での最小の形である。
